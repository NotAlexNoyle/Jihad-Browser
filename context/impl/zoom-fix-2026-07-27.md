# Zoom fix — magnify + visual-viewport pan (2026-07-27)

**Symptom (user, after rotation was confirmed working):** "zoom support is poor so things get
cut off." Kit: cavekit-offscreen-rendering R5 (zoom).

## Root cause

The daemon captures the page via `presShell->RenderDocument` into the PuppetWidget DrawTarget
(`UXP/widget/PuppetWidget.cpp JihadRenderDocument`). RenderDocument applies an internal
`scale = AppUnitsPerDevPixel / AppUnitsPerCSSPixel` that **cancels any engine zoom**. So both
the old `SetResolution(Z)` and `SetFullZoom(Z)` just relocated the content into a `1/Z` top-left
quadrant with the rest white — "cut off". Neither zoom API magnifies an offscreen RenderDocument
capture. (Proven on-device: `zoom 2.0` inject → content in the top-left ~384×470, unmagnified.)

## Fix

1. **Magnify (libxul):** `JihadRenderDocument(ds, zoom, panX, panY)` pre-scales the gfxContext by
   `Z` and renders a `(w/Z × h/Z)` CSS-px sub-rect, so `w/Z × h/Z` CSS px fill the `w × h` device
   buffer at `Z×`. The engine layout viewport stays at the window width (**no reflow**), so the
   old landscape 1.333 fit-zoom feedback loop **cannot** re-arm — rotation stays safe. Zoom +
   pan are passed on the extern-C `jihad_offscreen_render_document(widget, ds, zoom, panX, panY)`
   (5 args; both sides rebuilt). `GoannaRenderPage::SetZoom` just stores `mRenderZoom` — no
   SetResolution/SetFullZoom.
2. **Pan (document-relative — final approach after Codex review):** RenderDocument culls content
   outside the engine's display list, so a viewport-relative `aRect` pan goes blank past the first
   screen. `JihadRenderDocument` now renders with `RENDER_IGNORE_VIEWPORT_SCROLLING |
   RENDER_DOCUMENT_RELATIVE` when zoomed, so `aRect = (panX, panY, w/Z, h/Z)` is an **absolute
   document rect** — the whole page is reachable in BOTH axes with no display-list culling and no
   dependence on the engine scroll. `BrowserPageGoanna::setZoomAndScroll` / `setScrollPosition`
   just `SetRenderPan(vpX, vpY)` (clamped to content bounds) and leave the engine scroll alone.
   Pinch-zoom pan is a visual-viewport move (no `window.onscroll`) — correct mobile semantics.
   - **Is-zoomed threshold `|Z−1| > 1%`** on both the daemon and libxul: a near-1 fit-zoom (e.g.
     1.0052) stays on the **engine-scroll path** (`z≈1` → viewport-relative, `SetRenderPan(0,0)`,
     `ScrollTo`) so normal browsing keeps `window.onscroll` / `position:fixed` / `sticky` correct.
     Only a clear pinch/fit zoom uses the document-relative visual viewport.
   - An earlier engine-scroll + vertical-residual split was replaced after the Codex review (it
     echoed the parked engine scroll back to the adapter and corrupted the pan — F2/F4).
3. **Earlier (Codex F2):** `setScrollPosition` now divides scroll by zoom and updates
   `renderedX/Y` (it was feeding zoomed px to the CSS-px engine and advertising a stale origin).

## Verification (on device, via the daemon self-drive inject channel + frame.ppm)

- `zoom 3.0` → content magnified 3× (Y-bands 314 px tall). ✓
- `zoom 3 + scroll right (vpX 512)` → right portion of the page magnified. ✓ (horizontal pan)
- `zoom 3 + scroll to BOTTOM` → the page's last bands (Y=1700/1800/1900 of a 2000px page)
  render magnified 3× (was `bytes=0` blank with the engine-scroll split; document-relative fixed
  it). ✓ (vertical pan reaches the bottom)
- `zoom 1.0` → normal full page, text crisp. ✓ (no regression — the z≈1 path is the original
  viewport-relative capture)
- Rotation: unaffected by design (layout viewport untouched, no reflow, no feedback loop).

## Codex 5.6-sol adversarial review (2026-07-27) — all findings resolved

- **F1 HIGH — extern-C ABI mismatch (stale binary passes garbage).** FIXED: renamed the export to
  `jihad_offscreen_render_document_v2` (5 args). A daemon/libxul version mismatch now fails LOUDLY
  at RTLD_NOW load (undefined symbol) instead of mis-rendering. Verified: libxul exports `_v2`,
  daemon needs `_v2`, old symbol absent.
- **F2 HIGH — engine parking echoed as the visual scroll, corrupting pan.** FIXED: document-
  relative render ignores the engine scroll; the daemon no longer engine-scrolls when zoomed, and
  `emitScrollIfChanged` suppresses the scrolled-to echo while zoomed.
- **F3 HIGH — zoom-out clipped to the viewport.** FIXED: `RENDER_DOCUMENT_RELATIVE` renders a rect
  larger than the viewport; the is-zoomed threshold covers `z<1`.
- **F4 HIGH — split from stale cached height / assumed engine scroll.** FIXED: the engine-scroll
  split is gone; `mLastContentH/W` is now only a cosmetic pan clamp, not a correctness dependency.
- **F5 MEDIUM — fixed/sticky/onscroll inconsistency.** FIXED: pure visual viewport when zoomed
  (correct — pinch-zoom doesn't fire onscroll); near-1 fit-zoom stays on the engine-scroll path so
  normal browsing keeps onscroll/fixed/sticky.
- **F6 MEDIUM — horizontal overflow / unclamped pan → blank.** FIXED: document-relative never
  culls; pan clamped to content bounds on both axes.

**Note on the test harness:** the LIVE card's BrowserAdapter re-asserts its own zoom/scroll
within ~1–2 s, overriding injects — batch zoom+scroll in one inject, pull fast, and confirm via
the `[jihad-bs] painted … mZoom=` log line; or use the offline harness (`jihad-adapter-arm`) for
uncontested control. The end-to-end on-screen feel (adapter driving pinch → daemon magnify →
adapter composite at inv==1) is a human/gesture check (no gesture injection into LunaSysMgr).

## Follow-ups
- `mLastContentH` is cached (from emitGeometry); on a page whose height changes after the last
  geometry emit, the vertical-residual clamp could be briefly stale — refreshes on the next
  geometry emit. Acceptable; revisit if a tall dynamic page mis-clamps at the bottom.
- Horizontal pan assumes the full layout width is in the display list (true for device-width and
  fixed-width pages ≤ a few screens); extremely wide content could still cull — not observed.
