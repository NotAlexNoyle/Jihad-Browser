# cavekit-ipc-contract.md history, moved out of the kit by the 2026-11-07 sweep; verbatim.

## Scope (removed 2026-11-07)

The engine-agnostic render daemon and its contract with the BrowserAdapter: the
YAP command/message interface, the shared-memory framebuffer protocol, the
daemon lifecycle/page manager, and the LunaService surface. The **command/message
interface is frozen**: the port hinges on the YAP commands and messages staying
byte-identical so the UI needs no change. The self-contained build does rename the
adapter's NPAPI MIME and YAP *server socket name* for coexistence with the stock
browser (see R5, `jihad-self-contained-arch.md`) — a transport-addressing rebrand
that leaves every command/message signature untouched. Reference:
`docs/IPC-CONTRACT.md`, `context/refs/refs-overview.md`.

The addition is optional in BOTH directions, which is what makes it safe against a contract otherwise held byte-identical: an adapter that never sends it leaves the daemon on two buffers (`mKey3` stays 0 and every path behaves as before), and a daemon that does not implement it hits `BrowserServerBase`'s `default:` arm, logs `Unknown async cmd` and continues — the server-side declaration is a non-pure virtual with an empty body for exactly that reason. Old-with-new works in either combination; only two new halves engage the third buffer, and both ship in one `.ipk`. Rationale and measurements in docs/IPC-CONTRACT.md; the user authorised the change on 2026-08-10 to fix Flash frame rate. ## R4, criterion 1 (clearCache/clearCookies as a Luna service) (removed 2026-11-07)

 *(2026-08-05 — done, under a per-variant name rather than `com.palm.browserServer`, which is the stock daemon we coexist with. Proven on device: the daemon logs `luna: serving palm://net.riverstonerelay.jihadBrowser/{clearCache,clearCookies}`, `luna-send` to that URI returns `{"returnValue":true}`, and — the decisive part, because a `true` from the STOCK browser is exactly the false pass this criterion was written around — **our own daemon logs `luna: clearCookies` and `luna: clearCache`**, i.e. the hub routed the call to us and our handlers ran. Those handlers call the same `jihad::ClearCookies`/`ClearCache` the YAP commands already use. **And the ACTION is proven on a NON-EMPTY store** (2026-08-05, second run): three real cookies seeded through the cookie SERVICE (`nsICookieService::SetCookieString`, i.e. Set-Cookie semantics — not a synthetic row), giving `cookie count=3`; then `luna-send … /clearCookies` returned true with `luna: clearCookies` in our log; then `cookie count=0`. Registration, routing and deletion are each observed separately. One practical note for re-running it: the inject channel needs a live PAGE, so the card must be launched AT a url first (`params.target`) — with no page every `cookie` command is dropped with `inject: no page`, which reads exactly like a broken cookie store. **Three things had to be right, and each was wrong first:** (1) the service NAME may not contain a hyphen — LS2 rejects it at the caller with `_UriParse: Not a valid service name`, before any daemon sees it, so `jihad-browser` became `jihadBrowser` (camelCase, matching `com.palm.browserServer`); (2) the hub needs prv+pub role files keyed on `exeName`, which is the BUNDLED LOADER `ld-2.23.so`, not `jihad-browserserver`, since the job execs through it; (3) `LSMethod` on this device has THREE fields — the TouchPad ships luna-service**2**, not the LS1 shape the in-workspace luna-sysmgr sources use — and a two-field struct makes the library walk the table at an 8-byte stride where it reads 12, so registration SUCCEEDS while registering nothing and every call answers `Unknown method "clearCookies" for category "/"`.)*
  *The clearing itself is NOT missing: `asyncCmdClearCache`/`asyncCmdClearCookies` exist over YAP and are implemented in the daemon (`jihad::ClearCache/ClearCookies`). What is missing is a route from the card to them — the isis adapter exposes no scriptable `clearCache`/`clearCookies`, which is why the app uses the Luna URI. Two ways out, and it is a CONTRACT decision rather than a bug fix: register a per-variant service (`palm://net.riverstonerelay.jihad-browser/...`) and point each app at its own — a documented divergence like the MIME/YAP rebrand — or expose the two as scriptable adapter methods, which widens the frozen app-facing call set.*

  ***DECISION, 2026-08-04: register a PER-VARIANT service. This is no longer an open choice.*** *It
  is not a coin flip once the project's own precedent is applied: the second option widens the
  `callBrowserAdapter` set, which cavekit-ui-shell.md R2 holds byte-identical to upstream and marks
  MET — so taking it would knowingly break a met criterion in another kit. The first option is the
  same move already made, deliberately, four times over for coexistence: our own NPAPI MIME, our own
  YAP service name, our own upstart job, our own state directory. A Luna service name is the fifth
  instance of one pattern, not a new kind of divergence, and it leaves the app-facing contract
  untouched. **What implementing it takes:** the daemon registers `palm://net.riverstonerelay.jihad-browser{,-mochi,-mojo}/`
  with `clearCache` + `clearCookies` routed to the existing `jihad::ClearCache/ClearCookies`, name
  derived from `JIHAD_BS_NAME` like every other per-variant identity; each app's Preferences points
  at its own URI. Note there is no `lunaservice.h` in the sysroot — the device has
  `/usr/lib/liblunaservice.so` but no headers here — so the practical route is `dlopen` + the handful
  of `LS*` entry points, which also keeps the daemon loadable if the library is ever absent.
  Add `plan-variant-identity.md`'s table as the single source for the new name.)*
