## R3, criterion 1 (load-started then incremental progress) (removed 2026-11-07)

 *(2026-07: progress is real aggregate byte progress from the engine's progress listener, held to 1..99 while in flight so the client's progress bar visibly advances; 100 is sent only on genuine completion. Previously only 0 and 100 were ever emitted, so a slow load's bar sat frozen at 0% and read as a crashed "loading screen" — the platform's #1 usability complaint on 512 MB devices.)*

## R6, criterion 2 (link-clicked on tap) (removed 2026-11-07)

 *(**2026-08-04 — the MESSAGE is now observed, which is what this criterion asks for and what every earlier record was missing.** A tap on a relative-href anchor logs `linkClicked -> card: http://127.0.0.1:8731/target.html` (the href RESOLVED to an absolute URL, as the card needs) and the navigation then completes to that page with `back=1`. `msgLinkClicked` had no log line of its own until now, so the emission was invisible even when it happened; it has one at both call sites. **A trap this exposed, for anyone writing the next test:** the `clickid`/`dblclickid`/`clickoff` inject commands call `GoannaRenderPage::ClickAt` DIRECTLY and therefore skip the input QUEUE — and `TakeClickNav` is consumed in `pump()`, so those commands never produce a link-clicked message and never re-drive the navigation. The first run of this test showed exactly that: the anchor hit-tested, the engine started a load, it ended `NS_BINDING_ABORTED`, and nothing was emitted. Use `click <x> <y> <n>` (card coordinates, the real path) for anything about navigation semantics; `clickid` and friends are for reaching chrome controls.)* *(Historical detail preserved: *(review #5 H-2: the tap-interception path bypasses the engine's programmatic-load classifier, so the message must be emitted at interception.)* *(T5 ROOT FOUND + FIXED 2026-07-20 (2be6d85): "link taps show the loading overlay but nothing appears / overloads the browser" was the daemon CRASHING. Fixed with an `if (mInTick) return;` re-entrancy guard in tick(). Verified on device: the google/ddg tap+Enter sequence that gave 36 daemon restarts now gives ZERO. Also resolves the un-clickable search suggestions and html.ddg "still loading". [~] pending a full user re-test of link-tap navigation. See context/impl/device-test-2026-07-19.md.)* *(2026-07-31 reconciliation: link-tap navigation HAS since been confirmed on device — commit d4f0842 (2026-07-27) records "a tap on example.com's 'Learn more' link now hit-tests the anchor and navigates", after the zoom coordinate-consistency fix that was the second cause of missed taps (cavekit-input-bridging.md R5, `../impl/zoom-fix-2026-07-27.md`). Stays `[~]` because that record confirms the NAVIGATION, not this AC's actual subject — that the interception path EMITS the link-clicked message with the target URL — and no broad real-site re-test is recorded.)* *(2026-10-01 (third session), CE: coordinate tap at the 0.78 fit zoom — `clickAt (271,545) <A> href=file:///tmp/jihad-plain.html nav=1` → `linkClicked -> card: file:///tmp/jihad-plain.html`.)*
