# Cavekit: Browser Services

## Scope
Page-level services the engine must provide behind the existing contract:
settings/preferences, cookie and cache management, JavaScript dialogs,
downloads and MIME handoff, and TLS/certificate error handling. Reference:
`docs/IPC-CONTRACT.md` (settings, dialog, download, SSL messages),
`render/goanna/PORT-MAP.md`.

## Requirements

### R1: Engine settings applied
**Description:** Settings commands change engine behavior.
**Acceptance Criteria:**
- [x] `setUserAgent` changes the User-Agent sent on subsequent requests (verifiable via an echo endpoint or local server log).
- [x] `setEnableJavaScript` enables/disables script execution.
- [x] `setMinFontSize` enforces a minimum rendered font size.
- [x] `setBlockPopups` and `setAcceptCookies` take effect.
**Dependencies:** none

  - `CertGetDatabaseStrValue(int idx, CERT_DATABASE_ITEM_SERIAL, char* buf, int len)` — `:180`; the serial comes back as a HEX STRING (`strtol(...,16)`), not an int.
  - `makePathToCert(int serial, char* buf, MAX_CERT_PATH)` — `:185`; lower-case, so it is from the PRIVATE header `cert_mgr_prv.h`, not the public one the Makefile's `-isystem` advertises.
  - `CertPemToX509(const char* path, X509**)` — `:190`.
  - `CertInstallKeyPackage(const char* pemPath, NULL, char* passPhrase, int* serial)` — `:1981` and `:2004`; installs a PEM and returns its serial.
  - `CertAddAuthorizedCert(int serial)` — `:1986`, the PERMANENT arm. Upstream's own comment says THIS one, not `CertAddTrustedCert`, creates the correct openssl hash symlinks; `CertAddTrustedCert` sits commented out one line above at `:1984`. Do not swap them.
  - `CertAddTrustedCert(int serial)` — `:2006`, the SESSION arm.
  - `CertRemoveCertificate(int serial)` — `:335`; the dtor sweeps `temporaryCertSerials`, and that list is the ONLY thing that undoes a "trust once". Upstream's own comment at `:1904-1910` flags the leak: a daemon that dies without destructing turns every session cert permanent.

  **Store root `/var/ssl`, and it is group-owned, not app-owned.** `../ref-BrowserServer/Src/Main.cpp:274-281` `system()`s `chmod -R g+w /var/ssl; chown -R root.luna /var/ssl` at startup. Whether our upstart-launched daemon is in group `luna` is UNVERIFIED and is the first thing to check on device — a write path that silently EACCESes will look exactly like "the cert didn't take".

  **`com.palm.certificatemanager` is real, but it is the CARD's face and is read-only as far as this tree shows.** `app/source/CertificateDetail.js:198-199` calls `getcertificatedetails{certificateFilename}` (inherited from isis, unchanged in our fork), and the webOS 3 SDK's own Enyo framework calls `listcertificates` → `{userCertificateStore:[{certificateId, certificateFilename, commonname, organization}]}` (`build/webos-oe/pdk/opt/PalmSDK/0.1/share/framework/enyo/1.0/framework/lib/wifi/wifi.js:222` and `:791-799`). No install/add/remove method appears anywhere in the SDK, `luna-sysmgr`, or either reference clone — that is the one identification gap left. **So: the WRITE path is the library, the READ-for-display path is the service.** Our role files already grant `outbound:["*"]` (`packaging/gen-variant-scripts.sh:261`), so the service side needs no packaging change.

  **dlopen is the route, and ABI forces it independently of the missing headers.** The precedent is `render/browserserver/JihadLunaService.cpp:200` — `dlopen("liblunaservice.so", RTLD_NOW|RTLD_GLOBAL)`, typedef every entry point, NULL-check them all, degrade to "no service" instead of failing to start. The second reason here: **the daemon must not link OpenSSL.** `build/webos-oe/build-daemon-arm.sh` links only `-lxul -lmozglue -lnspr4 -lplc4 -lplds4 <glib> -ldl -lpthread`, the ARM sysroot ships `libssl.so.1.0.0`/`libcrypto.so.1.0.0`, and the DEVICE has 0.9.8 (cavekit-addons-extensions.md R7's Flash dependency audit). `-lssl/-lcrypto` would bake a SONAME the TouchPad does not have. `libPmCertificateMgr.so` links the device's own 0.9.8 and is safe to dlopen, but passing `X509*` across that boundary is not — so upstream's `findSSLCertInLocalStore`/`X509_cmp` half has to be reimplemented as a **DER byte-compare** against the PEMs the store enumerates.

  **What we already hold:** `PageChrome::NotifyCertProblem` (`render/goanna/GoannaRenderPage.cpp:171-194`) captures the real `nsIX509Cert` plus host/port, and `nsIX509Cert::getRawDER` (`third_party/uxp/security/manager/ssl/nsIX509Cert.idl:208`) yields the DER — so producing the PEM that both the store and `getcertificatedetails` want needs base64 and the BEGIN/END armour and nothing else. **What does not exist at all:** nothing in this port READS the platform store. NSS trusts its built-in roots plus the profile DB and never consults `/var/ssl` or `/etc/ssl/certs`, so an enterprise CA the user installed through the Certificate Manager app is INVISIBLE to Goanna today. That direction is `nsIX509CertDB::addCertFromBase64` / `importCertsFromFile` (`third_party/uxp/security/manager/ssl/nsIX509CertDB.idl:355, 218`) and is separate work from accept-and-share; cost it separately in T-135.

  **ALL THREE DEFECTS BELOW ARE FIXED, 2026-08-15 (T-135), desktop-verified end to end.** The line numbers in the paragraph are the PRE-FIX ones and no longer resolve. (1) certFile is a real armoured PEM whose fingerprint matches the server's certificate. (2) the code is a card ordinal, and it is derived from `nsISSLStatus` flags rather than the nsresult, because the nsresult turned out to describe the transport and not the certificate — `0x805a2fe3` is `SSL_ERROR_BASE + 29`, "malformed server hello". (3) the three-way answer is plumbed: `answer=1` produces `RememberValidityOverride(…, permanent)` and a `cert_override.txt` entry in the profile, `answer=2` produces the session form and no file at all. Details in the first AC of this R5 and in `../impl/impl-cert-store.md`.

  **Three live defects T-135 must fix, found by reading, not measured.** (1) `render/goanna/BrowserPageGoanna.cpp:1266` passes an EMPTY certFile, which is what makes the AC above only partly met. (2) The error code we pass is an nsresult in a card that expects Palm's small ordinal space — see that AC. (3) `awaitDialogReply` collapses "1" (Trust Always) and "2" (Trust Once) into one bool (`BrowserPageGoanna.cpp:1106`) and `AcceptCurrentCert` hardcodes `/*temporary*/true` (`GoannaRenderPage.cpp:1770-1771`) — so "Trust Always" does not survive a daemon restart even in Goanna's OWN store, let alone the platform's. The isis card has offered a three-way answer since upstream; the daemon has never been able to act on it.

  **Trap for whoever greps next:** `render/browserserver/Src/BrowserServer.cpp:161` and `Src/Main.cpp:274-281` still carry the upstream `USE_CERT_MGR` block, and NEITHER FILE IS COMPILED — `build/desktop/build-daemon.sh` and `build/webos-oe/build-daemon-arm.sh` list only `Src/BrowserServerBase.cpp`, `JihadBrowserServer.cpp`, `JihadLunaService.cpp` and the top-level `render/browserserver/Main.cpp`. Finding `CertInitCertMgr` in our tree is not evidence that anything calls it.

  **The one fact that needs hardware:** whether `libPmCertificateMgr.so` is present on webOS 3.0.5 at all — the recipe above is Open-webOS-era and the TouchPad runs HP's 3.0.5 build. One device line settles it (`ls /usr/lib/libPmCertificateMgr.so*` plus `nm -D` for the nine symbols). If it is absent, the fallback is file-level: write the PEM into the store directory ourselves and let `com.palm.certificatemanager/listcertificates` prove it took.
