# Cavekit: GPU Rendering (the pick: 2 + 4)

## Scope
The page is composited on the TouchPad's GPU (the Adreno 220, through EGL) by the engine's own
OpenGL compositor running inside the headless daemon, and the finished frame is read back into the
YAP shared buffer the card already shows (option 4). WebGL then runs on the same GPU through EGL
(option 2). The BrowserAdapter↔BrowserServer contract stays byte-identical: the card receives the
same buffers and messages as from the software path, only faster. All three interfaces (Enyo,
Mochi, Mojo) get it; the software path stays as the fallback.

**User decisions:** 2026-10-17, *"the pick: 2 + 4"* (GPU compositor with readback, then WebGL through EGL) after a
one-week spike (T-502); 24 fps video is acceptable and styled video matters (fades, rounded corners, video under a
modal), so the video overlay (5) is held back; the chart's speeds are *"the bare minimum goal"*, not the maximum.
2026-10-18, the owner's finger test on the GPU path: *"areas turn grey and zoom rendering of page content lags behind
actual page zoom state"* (R3, R6).

**The chart's rows for 2 + 4 (the floor, not the target):** animation and in-band scroll 42 ms
(24 fps); new content 106 ms (9 fps); WebGL 42 ms (24 fps); video decode plus a 42 ms frame. The
whole account, the measurements and the traps: `docs/RENDERING-OPTIONS.md` ("T-502").

## Requirements

### R1: The GPU path is the default, with the software path as its fallback
**Description:** The daemons of all three interfaces composite on the GPU unless it is unavailable.
**Acceptance Criteria:**
- [x] `packaging/event.d/{jihad,jihad-mochi,jihad-mojo}` (or the daemon's own default) start the GPU path; `JIHAD_GPU_COMPOSITOR=0` (and a pref the bundle reads) forces the software path *(2026-10-19, T-510: the generated jobs set `JIHAD_GPU_COMPOSITOR=1 JIHAD_GPU_EXPRESS=1`; the daemon settles the path before the engine starts (`render/browserserver/Main.cpp`): `JIHAD_GPU_COMPOSITOR=0` or `user_pref("jihad.gpu.enabled", false)` (default `true`, `packaging/prefs/jihad-platform-prefs.js`) selects the software path, and the log names the path taken and why. On the bench: all three jobs on the GPU path; the pref and the variable each put a daemon on the software path and back.)*
- [x] A daemon whose EGL setup fails (simulated by an env that makes the context creation fail) renders every page by the software path, and the startup report names the path taken *(2026-10-19, round 230: `JIHAD_GPU_TEST_NO_EGL=1` (engine 0047): the engine falls back to its software compositor, the daemon finds three frames failed and logs "the GPU path is off for this daemon (the compositor failed three frames): the software path renders from here"; the page renders; pages made later start in software)*
- [x] No GPU wait is unbounded: a stuck job is abandoned after a bound and the page falls back to the software path for that daemon's life; LunaSysMgr never loses EGL because of the daemon (memory `gpu-wedge-needs-a-reboot`) *(rounds 229-230: `JIHAD_GPU_TEST_STALL=30` holds a job 6 s; at 3 s (`JIHAD_GPU_JOB_BOUND_MS`) the daemon forgets it (the compositor then writes nothing into its slot) and paints in software; LunaSysMgr kept its EGL in every run, no "EGL error" in the system log. A driver call that never returns cannot be tested safely: the page goes on in software, the stuck compositor thread stays stuck)*
- [x] Enyo, Mochi and Mojo each load, pan, zoom and close a page on the GPU path on the bench (CE 3.1.0) *(2026-10-19, `tools/device/t502/default-check.sh` on each variant's own upstart daemon, desktop en.wikipedia.org driven through the card's self-test hook (drags, a flick, pinches, a double tap): each card closed, no fault, no fallback; the screenshots at rest sharp and covered)*
**Dependencies:** offscreen-rendering R1-R6, device-build R4
